# Centibot 产品与开发补充评审

评审日期：2026-10-19。范围：当前仓库的产品说明、桌面界面源码、Agent/任务/RAG 实现及本地验证脚本。以下区分代码事实与建议；未进行真实用户访谈、真实模型质量评测或桌面交互验收，不能据此声称已有线上成功率。

实施进度：P0-01 的工具过滤、执行时权限检查、后台任务继承及权限编辑入口已落地；P0-02 已增加工作区授权、路径与链接检查、现有文件确认、备份恢复及安全 ZIP 处理，详见 [实现与边界](agent-permissions.md)。下文保留评审时的问题依据；操作系统级隔离、目录事务恢复与其他 P0 项继续待办。

## 1. 产品判断

Centibot 已具备本地 AI 工作台的主要组件，但产品闭环仍然偏重“配置能力、调用工具、展示结果”。下一阶段应围绕“用户交付一个目标，系统在明确边界内完成，并提供可验收成果”组织产品。

建议首批聚焦中文知识工作者，主打两个场景：

1. 文档核对：选择本地资料 → 提问/对比 → 逐项结论与原文证据 → 导出审阅结果。
2. 资料研究：给定主题与来源范围 → 收集资料 → 生成有出处的报告 → 验证并保存成果。

本地文件整理可以作为后续场景，需要先完成路径授权、变更预览与恢复机制。开发者、知识工作者、自动化用户不宜同时作为首版验收对象；代码审查、微信入口、浏览器、多 Agent 分别会引入新的质量标准。

## 3. 按优先级排列的缺口

### P0-01：权限配置尚未形成执行约束

依据：`storage.ts` 的 `AgentProfile.tools` 包含 `enabledToolNames`、`allowNetwork`、`allowWrite`、`allowDelete`、`requireConfirmationForRisky`，但当前这些字段的引用主要位于类型、默认值和存储归一化；`ToolExecutor.ts` 依据全局工具策略执行，没有接收 Agent 权限上下文。仅保存字段无法保证限制生效。

补充：构建主进程生成的 `ExecutionContext`，带入 agentId、runId、授权工作区和有效权限。有效权限取应用、Agent、任务授权的交集。工具列表在提供给模型前过滤，真正调用时再次校验；未知工具或缺少策略的工具默认拒绝。前端隐藏按钮、提示词约束均不能代替执行检查。

验收：关闭网络后，即便模型直接返回 `fetch_url`，也不能发起请求；聊天、后台任务、预调用路径均通过同一检查；旧 Agent 数据迁移有明确默认行为。

### P0-02：文件保护依赖系统目录黑名单

依据：`tools/policy.ts` 使用系统环境变量形成保护根目录，缺少用户选择的工作区白名单；多数写入、替换、移动工具默认无需确认。这不能防止误改用户其他目录，跨平台与符号链接边界也需要单独验证。

补充：只读授权、允许创建、允许修改、允许删除分别建模；路径校验覆盖真实路径、父目录、符号链接/junction 和目标平台的大小写语义。覆盖、批量移动/替换展示目标清单和 diff；提供备份或回收站及恢复入口。确认绑定规范化参数摘要与有效期，参数变更后失效。

验收：`..`、链接越界、工作区外目标被拦截；拒绝确认不会产生文件变化；批量执行显示部分成功与失败，并可恢复已修改文件。

### P0-03：“本地优先”需要准确的数据边界

依据：README 同时声明支持在线模型以及“不会上传任何内容”；在线模型调用会向配置的服务发送请求内容。`storage.ts` 的在线配置含 `apiKey`，`saveModelSettings` 将配置写入 JSON；`trace.ts` 将工具参数交给日志，`logger.ts` 直接序列化 extra。

补充：在输入区显示本轮实际服务商、本地/在线状态，以及将发送的附件或知识库片段范围；提供强制本地模式，在线降级必须重新满足数据授权。密钥使用适配当前 Electron 版本的系统凭据保护，读取失败明确报错。日志统一脱敏，备份默认排除密钥，提供保留期限和清理入口。

验收：密钥不出现在明文配置、日志和默认备份；强制本地模式下不调用外部模型或联网工具；切换在线时明确告知数据范围。

### P0-04：有输出不等于任务完成

依据：`taskRunner.ts` 在执行返回后检查 `task.result.trim()`，随后设置 `completed`；成果路径通过工具返回文本等方式收集。这里没有独立的需求验收契约。`fileTools.ts` 部分工具捕获异常后返回“失败”字符串，而执行器仍可能记录为正常 `tool_end`。

补充：任务包含目标、输入范围、交付格式、必须满足的要求；工具统一返回 `ok/data/error/artifacts`。加入确定性验证节点：文件存在、格式可读取、必需字段齐全、引用对应有效证据。文档视觉质量与内容质量分别验证；生成成功不能代替阅读验收。结果区区分完成、部分完成、失败与待用户处理，明确未完成项。

验收：只有道歉文本、空文件、无效 PPTX、工具失败文本不能显示完成；用户可以打开产物、查看验证结果并针对原成果修改。

### P1-01：checkpoint 还不足以支持可靠恢复

依据：重启将运行任务转 blocked，`resumeTask` 可重新调用 `runTask`；目前 checkpoint 保存节点、轮次、调用计数等元数据，没有完整持久化可恢复消息栈和工具副作用账本。

补充：先将线性执行拆为可持久化阶段，无须为所有任务强制 DAG。保存运行配置快照、消息状态、工具调用 ID、参数摘要、审批、结果与产物。每个有副作用的步骤记录执行意图和完成状态；遇到“操作可能完成但结果未写回”先核对，不能直接重试。只读操作可自动重试，写入和外部提交按幂等能力处理。

验收：在文件写入前后、模型返回前后、审批等待时分别中断应用；恢复后无重复写入、重复追加和旧审批复用。界面准确区分“重新运行”和“从已完成步骤继续”。

### P1-02：知识库需要证据链，而不只是引用提示

依据：`ragRetriever.ts` 返回临时序号、文件名、知识库名、内容和分数，没有在该返回契约保留稳定 documentId/chunkId/页码；混合打分为向量候选上的 0.7/0.3 加权。关键词只对向量候选评分，不能召回未进入候选的关键词命中文档，因此与独立的双路召回有区别。

补充：引用快照保留知识库、文档版本/hash、chunk ID、页码或段落位置；回答编号映射结构化证据，点击可看原文。加入独立关键词召回，再评估融合和 rerank 的收益；分数表示检索相关度，不展示为“答案可信概率”。证据不足时报告缺口；全文总结需覆盖多个章节，不能只扩充相似片段数量。

验收：每个引用均可定位；重建索引后旧回答仍可查看当时证据；覆盖无答案、跨文档冲突、相似文件名、中文专有名词和跨章节总结样本。

### P1-03：首次使用与任务过程缺少交付引导

依据：任务中心的主要入口是自由文本，用户需要理解模型、嵌入模型、知识库和任务之间的关系。现有 Agent/Skill 配置多于业务任务入口。

补充：首启检测 Ollama、模型与嵌入能力，按用户选择的场景提供下一步；允许先体验在线或示例流程。提供两个可编辑场景模板，模板收集输入、输出和限制。执行区显示当前动作、已得成果、等待原因、可取消入口；关键缺失信息才提问，普通任务默认直接运行，批量覆盖或外部提交先展示具体变更。

验收：新用户无需理解 RAG 或工具路由即可完成首个示例；缺模型、断网、缺资料均给出具体恢复动作；执行后能继续要求“根据刚才报告修改”。

### P1-04：模型调度缺少能力与预算契约

依据：已按 Chat/Agent/RAG 配置模型，也有工具调用轮次限制，但固定次数限制不能表达用户对时间、token、费用和成果质量的要求。

补充：建立模型能力描述，包括工具调用、视觉、上下文窗口、结构化输出；不具备能力时明确降级。任务级配置总时限、token 和工具次数，价格未配置时显示未知；在途费用为估算，返回 usage 后再核算。上下文按预算压缩，保留目标、用户约束、证据 ID 与执行记录。连续相同工具和参数触发循环检查。

验收：到达预算时保留阶段结果和未完成项；本地失败不会静默切到在线；长会话仍保留权限及目标；取消后不继续调度新步骤。

### P1-05：Trace 与评测需要衡量真实交付

依据：`ToolExecutor.ts` 为每次工具调用新建 traceId，跨模型和工具步骤缺少统一运行关联；日志同步追加且未见轮转清理。`scripts/run-evals.mjs` 明确模拟模型和外部 I/O，只验证行为契约，不能代表真实回答质量。

补充：runId 贯穿一次任务，步骤使用 spanId/parentSpanId；记录路由、审批、模型、耗时、token、验证结果与错误分类。保留现有确定性回归，另建固定资料和真实模型评测，记录模型、提示词、索引与数据集版本。质量评测与开发快速测试分开运行，避免把付费调用放入默认单测。

验收：可由一条失败任务定位关联步骤；诊断包默认脱敏；固定样本能比较检索命中、证据支持、格式和任务成功率；模型升级前完成同一数据集对比。

### P1-06：桌面交付与模块边界需加强

依据：已有 IPC 分组，但 `index.ts`、`App.tsx`、`taskRunner.ts` 仍集中多项职责；窗口设置 `sandbox: false`，IPC 多处直接接收 TypeScript 类型参数。类型声明不能代替运行时校验。

补充：在统一 IPC 注册层验证 sender、参数 schema、大小和业务权限；审计导航、外链协议及 CSP；评估启用 sandbox 对 preload 的影响并做迁移验证。模型、权限、备份、任务、知识库分离服务；把手机研究等专用启发式从通用任务执行器移到场景模板。按平台验证打包、原生 LanceDB 依赖、数据迁移、更新失败及旧版本恢复。

验收：非法 sender 和参数无法访问主进程能力；发布包在干净机器完成首启和知识库检索；升级失败保留原数据。框架升级按兼容性分步执行，不以“版本变新”代替发布验证。

## 4. 补充到产品规格的关键对象

以下是建议契约，尚未实现：

| 对象 | 必须具备的信息 | 负责解决的问题 |
| --- | --- | --- |
| TaskSpec | 目标、输入引用、范围、交付要求、验收项、预算 | 系统明确何时算完成 |
| ExecutionContext | runId、agentId、配置版本、有效权限、授权路径 | 各执行入口遵守相同边界 |
| ToolResult | ok、结构化数据、错误码、是否可重试、产物 | 工具失败不会被当作成功文本 |
| ExecutionRecord | 调用 ID、意图、审批、参数摘要、完成结果 | 中断恢复不重复副作用 |
| Artifact | ID、路径、类型、版本/hash、来源任务、验证状态 | 成果可打开、追溯和修改 |
| Citation | 文档版本、chunk ID、定位、证据快照 | 结论可核对且不会因重建失去来源 |
| Feedback | 任务 ID、失败类型、用户修正、是否采纳 | 用户反馈转化为回归案例 |

暂不需要同时引入微服务、多 Agent 和全新数据库。先围绕上述边界重构现有单机应用；只有实际并发与事务需求无法满足时，再决定持久层升级。

## 5. 迭代顺序与发布门槛

| 阶段 | 交付范围 | 退出条件 |
| --- | --- | --- |
| A：可信执行 | 权限执行闭环、工作区授权、数据边界、结构化工具结果 | P0 验收全部通过，拒绝授权无副作用 |
| B：可靠交付 | TaskSpec、成果验证、恢复账本、统一 runId | 中断恢复无重复副作用；失败不能误报完成 |
| C：场景试用 | 两个场景模板、引用阅读、首启检查、真实模型评测 | 固定集达标且目标用户能完成真实任务 |
| D：受控扩展 | MCP、版本化 Skills、可编辑记忆、更多模板 | 新工具沿用相同权限、预算、日志与验收机制 |

建议首轮准备 30 个固定场景：文档核对 10、研究报告 10、权限/取消/中断 10。所有边界样本必须通过，两个场景各至少 9/10 达到预先写好的验收项；该门槛是初期建议，不代表统计上足以证明生产稳定性。记录每个样本的模型和执行环境，不跨模型混算。

持续指标：首次有效成果所需时间、任务验收通过率、无需重跑的完成率、引用可定位率、取消后新增操作数、每次有效交付的耗时与 token。数据优先在本机汇总；对外遥测另行提供明确选择，不默认上传文档和对话。

本轮不将团队权限、插件市场、多 Agent 协作列为优先需求。MCP 能扩充工具来源，但无法代替交付质量和权限机制；新增连接器应在 A/B 阶段达标之后。
